# 共用工程工作流程

本文件是 Codex 與 Claude Code 在此 repository 內工作的共同作業程序，與專案無關，由範本管理（版本見 `TEMPLATE_VERSION`）。專案事實放 `AI_CONTEXT.md`，專案規則放 `project-rules.md`；**不要把專案細節寫進本文件**，否則範本更新時會被覆蓋。

目標不是產生看起來合理的程式碼，而是完成有證據、可驗證、可審查的變更。

## 任務路由

先判斷任務類型，再啟動所需流程。簡單問答不必走完整修改流程。

| 任務類型 | 必要流程 |
|---|---|
| 詢問、解釋、審查、狀態報告 | 理解 → 查證 → 回報 |
| 診斷問題 | 取得證據 → 重現 → 現況流程圖 → 根因 → 回報 |
| 修改程式 | 理解 → 探索 → 現況流程圖 → 決策審查 → 計畫（非單純需求要先歸到一個計畫並展開細項，見「計畫分開管理」）→ 實作 → 驗證 → 審查 → 回報（附修改後流程圖） |
| 效能改善 | 基準 → 量測 → 找瓶頸 → 最佳化 → 重新量測 |
| Commit | 確認驗證結果 → 精確 stage → 套用 `project-rules.md` 的 Git 規則 |

內部遵守流程，最終輸出保持精簡；除非有助於決策，不必逐項輸出每個步驟。

## 0. 交接（開工與收工）

Claude Code 與 Codex 會輪流在同一個 repository 工作，彼此看不到對方的對話。唯一的共同記憶是 repository 內的文件，每份文件的職責不重疊。3.0.0 起分成「專案」與「計畫」兩層：專案層只放整個專案的事實、規則與導覽；每個需求（計畫）的進度、變更紀錄、子任務各自放在自己的資料夾，不同計畫的紀錄不混在同一份檔案裡（規則見「計畫分開管理」）。

| 檔案 | 內容 | 寫入方式 |
|---|---|---|
| `AI_CONTEXT.md` | 專案事實 | 原地修改，很少變動 |
| `docs/architecture.md` | 系統結構 | 原地修改 |
| `docs/decisions.md`、`docs/adr/NNN-slug.md` | 設計決策與理由（ADR，跨計畫共用）：內容在 `docs/adr/`，`decisions.md` 只是索引 | 只新增，索引新的在最上方 |
| `docs/current-status.md` | 專案層級的快照：階段、跨計畫的已知問題與待使用者決定；**不放任何計畫的細節** | 原地修改，保持精簡 |
| `docs/plans/INDEX.md` | 計畫索引：每個計畫的編號、類型、名稱、狀態、位置、依賴、分支；下一個可用編號 | 新增或計畫層級的狀態改變時 |
| `docs/plans/<狀態>/<ID>-<slug>/plan.md` | 這個計畫的目標、範圍、細項表（單一事實來源）、完成定義、Commit 範本、Start prompt | 開工前建立；需求或細項變動時改 |
| `…/<ID>-<slug>/status.md` | 這個計畫「現在」的快照：目前細項、阻礙、待決定、下一步、接續資訊 | 每次有實質進度時原地修改 |
| `…/<ID>-<slug>/changelog.md` | 這個計畫的變更紀錄（每個 session 一筆） | 只新增，新紀錄在最上方 |
| `…/<ID>-<slug>/tasks/<ID>.<m>-<slug>.md` | （選用）細項的實作細節與驗收結果 | 該細項執行時 |
| `.ai/handoff.md` | 給下一位 agent 的交接單：上一個 session 動了哪些計畫、未提交的變更、不要動的東西 | 每次收工整份覆寫 |
| `docs/legacy/` | 3.0.0 之前的全域紀錄（舊 `current-status.md`、`changelog-ai.md`、`plan/`） | 封存，不再追加 |

**開工（非單純任務）**：讀 `.ai/handoff.md`、`docs/current-status.md` 與 `docs/plans/INDEX.md`，找出這次要處理的計畫（「計畫分開管理」的路由規則），**只讀那個計畫**的 `plan.md` 與 `status.md`（需要歷史時才讀它的 `changelog.md`）；要動架構時加讀 `docs/architecture.md` 與 `docs/decisions.md`。再看 `git status` 與相關的 commit，確認工作目錄與計畫的 `status.md` 一致；不一致時以程式碼與實際的測試結果為準，先釐清再修改。

**收工（有意義的變更之後）**：依 `ai-handoff` skill 更新：該計畫的 `plan.md` 細項表、`status.md`、`changelog.md`，計畫層級的狀態改變時才改 `INDEX.md`，最後覆寫 `.ai/handoff.md`。沒有改動任何程式或設計的問答，不需要寫交接。

規則：

- 不覆蓋另一個 agent 未完成的工作；先檢視 `git status`、`git diff` 與交接單。
- 工作目錄裡不是自己改的未提交修改，視為使用者資料，不清理、不回復、不一併 stage。
- `docs/adr/` 已記錄的決定，沒有新證據不推翻；要推翻就新增一筆，並在新舊兩筆都標明取代關係。
- 事實與推測分開寫；沒驗證的內容標明「未驗證」。

## 1. 理解

開始前確認：

- 使用者真正要達成的行為與驗收條件。
- 現況、受影響範圍、既有 interface 與回歸範圍。
- 任務只授權調查，還是已授權修改。
- 答案能否從程式碼、測試、文件、設定或 git 歷史取得；能就先查，不要先問。

不要因為某個解法看起來合理就立即修改。

## 2. 載入相關 context

依 `AI_CONTEXT.md` 的「Context Routing」選擇最少且足夠的文件與 skill。先搜尋現有實作與既有模式，再建立新抽象。避免一次載入所有文件；不相關的內容會稀釋重點。

## 3. 決策審查（非單純程式修改，在計畫前）

依實際會動到的範圍，逐項判斷下列面向是否受影響：

- 架構與模組介面
- 資料契約與生命週期
- 所有權與資源釋放
- 並行、順序與狀態
- 可靠性與錯誤處理
- 安全與信任邊界
- 效能與容量
- 交付、相容性與可觀測性
- 測試與驗證

被選中的每個面向，在計畫裡留下三件事：

1. **Decision**：受影響的不變條件或介面，以及採用的取捨；若確認不受影響，寫出具體理由。
2. **Evidence**：支撐判斷的呼叫流程、原始碼、量測或既有文件。
3. **Verification**：可觀察的結果、回歸測試或量測方式。

低風險的局部修改，每項一行即可。禁止用「已考慮」「應該沒問題」取代決策與證據。這份清單是最低集合，不是上限。

## 4. 先有證據再動手

診斷與修正必須區分：

- **Observed Fact**：編譯錯誤、失敗測試、log、stack trace、可重現的輸入輸出、profiler 或原始碼行為直接支持的事實。
- **Hypothesis**：仍待驗證的可能解釋，不得當成已確認的根因回報。
- **Conclusion**：證據足以解釋失敗機制與觸發條件的結論。

修正前至少取得一項具體證據；無法重現時，記錄限制與替代證據。

## 5. 範圍與根因

修改前確認：

- 哪些程式路徑與輸入會觸發問題，問題是局部或跨模組。
- 是否涉及所有權、生命週期、執行緒、座標或呼叫順序風險。
- 相鄰的呼叫點是否有相同缺陷。

追查鏈要走到底：現象 → 失敗機制 → 觸發條件 → 底層缺陷 → 根因。不要只修補第一個可疑位置。

### 流程圖（修改前後各一份）

跨函式、跨模組或跨執行緒的問題，只用文字描述程式路徑，讀者無法驗證你看懂了什麼。因此：

- **修改前**：先讀實際程式碼，畫出目前流程，節點標上檔名與函式名，並指出缺陷發生在哪個節點。圖必須從程式碼推導，不可憑命名猜測。
- **修改後**：畫出改完的流程，明確標出與修改前不同的節點（新增、移除、順序調整、條件變更）。

呈現方式：平台能在對話中渲染圖形時，就輸出渲染後的圖；不能時退回 Mermaid（`flowchart` 或 `sequenceDiagram`）。寫進 `.md` 文件的流程圖一律保留 Mermaid 原始碼。單一函式內的修正不必畫，判準是「讀者是否需要跨檔案追蹤才能理解這次改動」。

## 6. 計畫

非單純修改先建立短計畫：要處理的根因或目標行為、要修改的檔案、最小可行變更、回歸風險與驗證方式、決策審查的結論。避免無關重構；新資訊推翻原計畫時，先更新計畫再繼續。

計畫的細項要寫進該計畫 `plan.md` 的細項表，規則見下方「計畫分開管理」。

## 7. 實作

- 保留既有架構與公開介面，除非有證據必須改變。
- 遵守 `project-rules.md` 與周邊程式碼的慣例。
- 優先回傳可觀察的結果，避免只能從內部狀態判斷正確性。
- 不修改無關檔案；使用小而可審查的變更，並檢查受影響的呼叫點。

## 8. 回歸保護

修正 defect 時，能實作就加回歸測試。好的測試要：在原 defect 存在時失敗、覆蓋觸發條件或根因、修正後通過、從模組介面驗證可觀察行為。若硬體、授權、測資或環境使自動測試不可行，記錄替代驗證與剩餘風險。

## 9. 驗證

程式修改不是完成。驗證指令以 `AI_CONTEXT.md` 的「建置與測試」為準；該節沒有定義時，不要猜指令，向使用者確認，或在回報中標示 `NOT VERIFIED`。保留真實的 exit code。

驗證結果只使用三種：

- `VERIFIED`：所需檢查實際成功。
- `PARTIALLY VERIFIED`：部分檢查成功，仍有明確未驗項目。
- `NOT VERIFIED`：環境、硬體、權限、相依或時間限制使必要檢查未執行。

不得把「應該能過」「靜態看起來正確」或既有舊產物當成通過。失敗的檢查未排除前，不得宣稱完成。

## 10. 審查

完成前檢查：完整 diff 與非預期檔案、重複邏輯與錯誤處理、邊界條件、資源所有權與執行緒安全、公開介面相容性、殘留的 debug 程式碼與過期註解、缺漏的測試、文件是否需要更新。

## 11. 回報

非單純任務的最終回報包含：

- **Finding**：實際發現什麼。
- **Decision Review**：哪些面向被觸發，最後採用的決策與證據。
- **Changes**：修改了什麼。
- **Flow Diagram**：修改前與修改後（規則見第 5 節），需要跨檔案追蹤才能理解的改動必附。
- **Verification**：實際執行的命令與結果。
- **Remaining Risks**：未驗證、環境依賴或超出範圍的項目。
- **Handoff**：更新了哪些交接文件（含哪個計畫的哪些細項狀態變了）。

核心順序始終是「Context → Decision Review → Evidence → Reasoning → Action → Verification」，而不是「Assumption → Action → Confidence」。

## 計畫分開管理

使用者的需求不是一句話做完就算：非單純的需求先歸到一個**計畫**、展開成可追蹤的細項，再動手。每個計畫有自己的資料夾，進度、變更紀錄與子任務只寫在那裡，不同計畫的紀錄不混在同一份檔案，日後也好找。層級是「專案 → 計畫 → 細項 → 歷史」：

| 層級 | 放在哪裡 | 內容 | 什麼時候更新 |
|---|---|---|---|
| 專案 | `AI_CONTEXT.md`、`docs/architecture.md`、`docs/adr/`、`docs/current-status.md` | 專案事實、結構、跨計畫的決策、專案層級的快照 | 重大變更時 |
| 計畫 | `docs/plans/<狀態>/<ID>-<slug>/` | 一個需求的範圍、細項表、狀態快照、變更紀錄 | 每個計畫獨立更新 |
| 細項 | 計畫 `plan.md` 的細項表（必要時加 `tasks/<ID>.<m>-<slug>.md`） | 可執行、可驗收的工作 | 隨實作進度 |
| 歷史 | 計畫的 `changelog.md`；完成的計畫搬到 `completed/` | 已發生的變更與驗證結果 | 只新增 |

### 資料夾

```text
docs/plans/
├─ INDEX.md                    計畫索引（唯一的入口）：所有計畫與下一個可用編號
├─ _template/                  新計畫的範本（範本管理）：plan.md、status.md、changelog.md、tasks/_task.md
├─ active/<ID>-<slug>/         規劃中、進行中、暫停或受阻的計畫
│  ├─ plan.md                  目標、範圍、不做什麼、細項表、完成定義、Commit 範本、Start prompt
│  ├─ status.md                現在的快照：目前細項、阻礙、待使用者決定、下一步、接續資訊
│  ├─ changelog.md             這個計畫的變更紀錄（只新增，新的在上）
│  └─ tasks/                   （選用）細項的實作細節與驗收結果
├─ completed/<ID>-<slug>/      完成的計畫（整個資料夾搬過來，內容保留）
└─ cancelled/<ID>-<slug>/      取消的計畫（plan.md 寫取消的原因）
```

### 規則

- **編號**：計畫用 `Rnn`（兩位數字遞增，整個專案共用一個序列，不重用；下一個可用編號寫在 `INDEX.md`）。照總體計畫分步驟的專案，步驟本身也可以是計畫（例如 `S03`）。細項用 `<ID>.<m>`（例如 `R07.2`）。3.0.0 之前已經用過的編號照舊，不重新編。
- **路由（開工時先做）**：讀 `INDEX.md`，判斷這次的需求屬於哪個計畫：
  - 明顯屬於某個未完成的計畫 → 接著用它。
  - 和所有計畫都無關 → 新增一個計畫（從 `_template/` 複製，`INDEX.md` 加一列）。不要把無關的工作塞進舊計畫。
  - 是已完成計畫的後續或修改 → 開新計畫，在 `plan.md` 的「相關」寫上原計畫；不要重新打開舊的 `changelog.md`。
  - 符合兩個以上的計畫 → 先看各自的範圍、動到的程式與依賴；還是分不出來就問使用者。
- **一個細項只屬於一個計畫**。動到別的計畫管的設計或介面時，只在那個計畫的 `changelog.md` 記一筆「受影響的內容」並互相連結；不要把同一份紀錄複製到幾個計畫。
- **細項表是單一事實來源**：`plan.md` 的細項表欄位為「編號、細項、狀態、分支／commit、驗證」。新展開的細項一律先標 ⬜；開始做改 ⏳；完成時改 ✅，補上分支／commit 與驗證（`VERIFIED`、`PARTIALLY VERIFIED`、`NOT VERIFIED` 與實際跑了什麼）。範圍或做法變動時改細項文字，並在 `changelog.md` 記下原因。完成的列不刪除；取消的列標 ⛔ 並寫原因。
- **`status.md` 是快照，不是歷史**：只寫「現在」——目前在做哪個細項、阻礙、待使用者決定、下一步、接續資訊（換 agent 或換 session 時要知道的事），不重抄細項表，也不累積每天做了什麼（那是 `changelog.md`）。
- **`changelog.md` 只記這個計畫**：每個 session 一筆，新的在最上方，寫做了哪些細項、改了哪些檔案、實際跑的驗證與結果、commit；沒有執行的測試不可以寫「通過」。
- **`INDEX.md` 只做導覽**：每個計畫一列（編號、類型、計畫、狀態、位置、依賴／相關、分支）。只在新增計畫或計畫層級的狀態改變時更新，不放細項或進度描述；這樣多個 session 同時處理不同計畫時，比較不會在同一份檔案衝突。
- **計畫的狀態**：⬜ 規劃中 → ⏳ 進行中 →（⚠️ 受阻／暫停）→ ✅ 完成；⛔ 取消。完成定義全部達成才算 ✅：把資料夾從 `active/` 搬到 `completed/`（取消的搬到 `cancelled/`），更新 `INDEX.md` 的狀態與位置，搬動後跑 `check-ai-structure.ps1` 確認連結沒有斷。
- **專案層級不放計畫的細節**：`docs/current-status.md` 只寫整個專案的階段、跨計畫的已知問題與待使用者決定，並指向 `INDEX.md`。
- **小修改**：單一檔案的錯字、純問答、狀態詢問不必開計畫。其他「有意義的變更」都要屬於某個計畫（範圍很小的修正就開一個小計畫，細項只有一列也可以）。
- **委派規劃**：把規劃交給 architect 系列 subagent 時，由**主 agent** 把回傳的計畫寫進計畫資料夾與 `INDEX.md`；subagent 不直接修改這些文件。委派實作時，subagent 在回報裡逐項列出細項的結果，由主 agent 更新細項表、`status.md` 與 `changelog.md`。
- **收工**：依 `ai-handoff` skill 更新本次動到的計畫，並在最終回覆總結每個細項的狀態變化。
- **舊紀錄**：3.0.0 之前的全域紀錄（舊 `current-status.md` 的需求進度表、`changelog-ai.md`、`plan/`）搬到 `docs/legacy/`，只讀不追加；未完成的需求在遷移時拆成各自的計畫。

## 範圍與安全

- 使用者明確指示優先，但不得虛構驗證或隱藏失敗。
- 調查、說明與 review 不自動授權修改、commit、push、對外傳輸或操作實體設備。
- 破壞性動作、刪除、結束行程、對外發布與權限變更，必須符合平台的核准機制；工具允許不等於已獲授權。
